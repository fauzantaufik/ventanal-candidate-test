# Design: US-07 — Search-First Directory Homepage

> Temporary design doc. Archive after implementation is verified.

## Overview

Reshape the `web/` homepage so it feels closer to a Google Reviews–style discovery experience: a prominent search bar, fast scan-friendly business cards, and URL-driven filters that help visitors find relevant local services quickly. The implementation should stay incremental by extending the existing Next.js homepage and the current `GET /businesses` route rather than introducing a new search stack.

## Goals

- Make search the primary action on the homepage
- Support real business lookup by partial name or descriptive keyword
- Keep category filtering and pagination working with the new search flow
- Surface trust signals quickly: rating, review count, verification badge, and city
- Preserve a Spanish-first, warm local directory tone
- Keep the experience shareable and refresh-safe through URL query params

## Non-Goals

- Full Google Maps or map-based browsing
- Review-text search inside a business detail page
- Rebuilding the entire visual system or rebranding the app
- Adding advanced ranking, geolocation, or owner-response features

## Data Flow

```text
Homepage request
  └─ reads ?search=, ?category=, ?page=
       └─ getBusinesses({ search, category, page })
            └─ Hono route GET /businesses
                 └─ D1 query with optional WHERE clauses
                      └─ paginated results + total count
                           └─ homepage renders search summary and cards
```

## Proposed Changes by Area

### 1. Backend: extend the existing list query

Update `worker/src/routes/businesses.ts` so `GET /businesses` accepts an optional `search` string and applies it to both the main result query and the total-count query.

Recommended SQL behavior:

- `LOWER(b.name) LIKE LOWER(?)`
- optionally include `OR LOWER(b.description) LIKE LOWER(?)`
- preserve the current sort order: `b.verified DESC`, then `avg_rating DESC`

This keeps search additive and avoids a separate endpoint.

### 2. Frontend API contract

Update `web/src/lib/api.ts` and `web/src/app/page.tsx` so the homepage can forward:

- `search`
- existing `category`
- existing `page`

Use the current URL-driven App Router pattern instead of introducing a client-only search store.

### 3. Homepage layout (`home-content.tsx`)

Refactor the top of the page into a search-first discovery block:

1. **Title and subtitle**
2. **Prominent search form** with a placeholder like `Busca clínicas, restaurantes o servicios...`
3. **Category chips** below the search field
4. **Results summary row** showing active query/filter and a `Limpiar filtros` action
5. **Business grid** with the existing cards, but with clearer rating/review prominence

Suggested interaction model:

- user types a query and presses Enter or taps the search button
- the page reloads with the new URL params
- results remain shareable and server-rendered

This is the smallest reliable approach for the current architecture.

### 4. Business card polish

Update `web/src/components/business-card.tsx` so each result feels easier to scan at a glance:

- emphasize the business name
- keep the rating and review count near the title
- preserve the verified/premium badge
- keep city/category visible but secondary

The goal is familiarity and clarity, not copying Google’s exact UI.

## Request / Response Contract

### Request example

```http
GET /businesses?search=dental&category=salud&page=1
```

### Response shape

No new response shape is required. Reuse the current paginated list response:

```json
{
  "data": [
    {
      "slug": "clinica-dental-sonrisa",
      "name": "Clínica Dental Sonrisa",
      "city": "Caracas",
      "avg_rating": 4.8,
      "review_count": 24,
      "verified": 1
    }
  ],
  "meta": {
    "total": 1,
    "page": 1,
    "limit": 20
  }
}
```

## UI / UX Notes

- Keep the experience **Google-like in structure**, not in branding.
- Use the repo’s warm orange / stone palette rather than Google colors.
- All visible copy should remain natural in Spanish for Venezuelan users.
- If no results match, show a calm empty state with guidance to try another term or clear filters.
- Preserve existing loading and retry patterns instead of inventing new ones.

## Testing Plan

### Worker verification

Add or extend tests for:

- `GET /businesses?search=<term>` returns matching businesses
- `GET /businesses?search=<term>&category=<slug>` narrows results correctly
- no-match search returns an empty array with `meta.total = 0`
- existing pagination and ordering still behave correctly when `search` is absent

### Web verification

- `pnpm --filter web build`
- manual check on `/` for:
  - search by business name
  - search with category chip still applied
  - refresh/bookmark preserves the query
  - empty and error states remain clear in Spanish

## Risks / Notes

| Risk | Mitigation |
| --- | --- |
| Search is too broad or noisy when description matching is enabled | Start with `name` + `description`; adjust weighting later only if needed |
| Adding client-side instant search could complicate the App Router flow | Keep the first version URL-driven and submit-based |
| The UI may feel too generic if only a search bar is added | Also improve the result summary and trust-signal hierarchy on cards |
