# Design: US-06 — System Maintains Review Integrity

> Temporary design doc. Delete after implementation is verified.

## Overview

Enforce the rule that each authenticated user may submit only one review per business, while rejecting invalid or expired JWTs before any review write occurs. This story is the integrity layer behind US-05: the database stays the final source of truth, the worker returns precise Spanish HTTP errors, and the UI can safely explain why a submission was rejected.

## Goals

- Validate Supabase JWTs server-side before processing review submissions
- Return `401` for missing, invalid, or expired tokens
- Return `409` with a Spanish message for duplicate reviews
- Keep the existing D1 `UNIQUE(business_id, user_id)` constraint as the hard guardrail
- Ensure business aggregate fields (`avg_rating`, `review_count`) stay consistent after successful inserts

## Non-Goals

- Rate limiting or abuse detection
- Review moderation and content filtering
- Multi-review history or editing
- Changing the public `GET /businesses/:slug/reviews` behavior

## Integrity Flow

```text
Authenticated review submission
  └─ worker receives POST /businesses/:slug/reviews
       ├─ parse Authorization header
       ├─ verify Supabase JWT
       │    ├─ invalid / expired → 401
       │    └─ valid → extract user identity
       ├─ validate rating/comment payload
       ├─ resolve business slug
       ├─ attempt INSERT into reviews
       │    ├─ UNIQUE constraint hit → 409
       │    └─ success → recompute avg_rating + review_count
       └─ return 201 response
```

## Proposed Changes

### 1. JWT validation in `worker/src/routes/reviews.ts`

Keep the logic close to the route instead of creating a large auth subsystem. A small helper is enough:

```ts
async function getAuthenticatedUser(c: Context): Promise<{
  userId: string;
  email: string;
  userName: string;
}> {
  // read Bearer token
  // verify against Supabase JWKS
  // return normalized claims
}
```

Recommended implementation approach:

- configure the worker with the Supabase project URL (or JWKS URL)
- verify the access token against `/.well-known/jwks.json`
- reject missing, malformed, invalid, or expired tokens with `401`

This keeps the worker aligned with FR-03 and avoids trusting the client.

### 2. Duplicate prevention strategy

Use a two-layer approach:

1. **Database constraint remains authoritative**
   - `UNIQUE(business_id, user_id)` already exists in `migrations/0002_reviews.sql`
2. **Application maps the failure clearly**
   - catch the D1/SQLite constraint error and translate it to:

```json
{ "success": false, "error": "Ya has dejado una reseña para este negocio" }
```

A pre-check query may be added for friendlier early feedback, but it must **not** replace the DB constraint because concurrent requests can still race.

### 3. Business aggregate consistency

After a successful insert, update the business row from the canonical `reviews` table:

```sql
UPDATE businesses
SET avg_rating = (
      SELECT COALESCE(AVG(rating), 0)
      FROM reviews
      WHERE business_id = ?
    ),
    review_count = (
      SELECT COUNT(*)
      FROM reviews
      WHERE business_id = ?
    )
WHERE id = ?;
```

This keeps `avg_rating` and `review_count` accurate even if the first review is inserted or later failures occur.

### 4. Error contract for the frontend

The worker should return stable Spanish errors that `ReviewForm` can map directly:

| Status | Meaning                         | Message                                             |
| ------ | ------------------------------- | --------------------------------------------------- |
| `400`  | invalid payload                 | `La reseña enviada no es válida.`                   |
| `401`  | missing / invalid / expired JWT | `Tu sesión no es válida. Inicia sesión de nuevo.`   |
| `404`  | unknown business slug           | `Negocio no encontrado`                             |
| `409`  | duplicate review                | `Ya has dejado una reseña para este negocio`        |
| `500`  | unexpected server issue         | `No se pudo guardar la reseña. Inténtalo de nuevo.` |

## Config / Environment Notes

Because the current `worker/wrangler.toml` only defines `ENVIRONMENT`, implementation will also need auth configuration available to the worker, for example:

- `SUPABASE_URL` or `SUPABASE_JWKS_URL`
- any additional JWT verification metadata required by the chosen library

Keep these as runtime env vars rather than hard-coding them in the route.

## Testing Plan

### Worker (Vitest)

Add / extend tests to prove the integrity guarantees:

- request without `Authorization` header returns `401`
- request with invalid or expired token returns `401`
- first valid review inserts successfully with `201`
- second review from the same `user_id` for the same business returns `409`
- duplicate attempts do not create extra rows in `reviews`
- business `avg_rating` and `review_count` match the actual stored reviews after success

### Web (manual)

- Logged-in user who already reviewed sees a graceful locked message instead of a broken form state
- Expired session redirects the user back to login when trying to submit again

## Risks / Open Questions

| Risk                                                                        | Mitigation                                                                              |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| JWT verification requires worker-side configuration that is not yet present | Add the minimal env vars in `wrangler.toml` / deployment settings during implementation |
| Catching only a pre-check query could still allow race-condition duplicates | Keep the database `UNIQUE` constraint as the final source of truth                      |
| Backend errors could leak raw SQLite messages                               | Normalize all known failures into stable Spanish JSON responses                         |
