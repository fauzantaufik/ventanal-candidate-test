# Design: US-04 — Consumer Logs In

> Temporary design doc. Delete after implementation is verified.

## Overview

Implement `/auth/login` as the returning-consumer entry point for Supabase Auth. The page should accept email and password, show Spanish validation and error states, preserve the `returnTo` query parameter, and rely on Supabase session persistence so later review submissions automatically have a JWT available.

## Goals

- Build a complete login form with `email` and `password`
- Redirect the user back to `returnTo` (or `/`) after successful login
- Show invalid-credential and network errors in Spanish
- Keep the UX aligned with the existing card-based Next.js UI and shadcn-style primitives
- Ensure the browser session is ready for later authenticated API calls from `ReviewForm`

## Non-Goals

- Account creation flow (US-03)
- Password reset or magic-link login
- Social auth providers
- Worker-side JWT validation logic itself (consumed later by US-05 / US-06)

## Affected Areas

| Workspace | Files                            | Change                                                        |
| --------- | -------------------------------- | ------------------------------------------------------------- |
| `web/`    | `src/app/auth/login/page.tsx`    | Replace the stub with the real login page                     |
| `web/`    | `src/lib/supabase.ts`            | Reuse the existing Supabase client; no contract change        |
| `web/`    | `src/components/review-form.tsx` | Reuse the stored session after login; no direct login UI here |
| `web/`    | `src/app/auth/signup/page.tsx`   | Link back and preserve `returnTo` convention                  |

## User Flow

```text
Anonymous or returning consumer
  └─ opens /auth/login?returnTo=/{slug}#reviews
       └─ enters email + password
            ├─ invalid input/client error → inline Spanish feedback
            ├─ invalid credentials → error alert on the same page
            └─ success
                 └─ Supabase stores session in browser
                      └─ router.replace(returnTo || '/')
```

## Proposed Changes

### 1. `web/src/app/auth/login/page.tsx`

Convert the current stub into a client page (`'use client'`) using:

- `useRouter()` for navigation
- `useSearchParams()` to read `returnTo`
- controlled local state for `email`, `password`, `submitting`, and `error`

**Submit flow:**

```ts
await supabase.auth.signInWithPassword({ email, password });
```

On success:

1. read `returnTo`
2. validate it is an internal path (must start with `/`)
3. `router.replace(destination)`

If `returnTo` is missing or malformed, fall back to `/`.

### 2. Safe redirect handling

Use the same convention introduced by US-02 / US-03:

```text
/auth/login?returnTo=%2Fpanaderia-la-esquina%23reviews
```

Guard against open redirects by allowing only app-internal values:

```ts
const destination = returnTo?.startsWith("/") ? returnTo : "/";
```

### 3. UI structure

Use a simple, shippable auth card:

- `Card` / `CardHeader` / `CardContent`
- `Label`
- `Input`
- `Button`
- `Alert` for errors

If the repo does not yet contain `components/ui/*`, only scaffold the small subset needed for this page during implementation.

Suggested layout:

```text
┌────────────────────────────────────┐
│ Iniciar sesión                     │
│ Accede para dejar tu reseña        │
│ [ Correo electrónico            ]  │
│ [ Contraseña                   ]   │
│ [ Ingresar ]                       │
│ ¿No tienes cuenta? Crear cuenta    │
└────────────────────────────────────┘
```

### 4. Session persistence and JWT usage

No manual token storage should be added. `@supabase/supabase-js` already persists the session in the browser. Later authenticated requests (US-05) should obtain the access token from the active session and send:

```http
Authorization: Bearer <access_token>
```

That satisfies the acceptance criterion that the JWT is stored and attached to subsequent API requests.

## UI / UX Notes

- Keep all text in Spanish.
- Disable the submit button while the request is in flight and show `Ingresando...`.
- The password field must use `type="password"`.
- Prefer short, readable errors over raw Supabase provider messages.
- Include a secondary link to `/auth/signup`, preserving the same `returnTo` parameter.

## Error Handling

| Situation                  | UI message                                       |
| -------------------------- | ------------------------------------------------ |
| Missing email/password     | `Completa tu correo y contraseña.`               |
| Invalid credentials        | `Correo o contraseña incorrectos.`               |
| Network / provider failure | `No se pudo iniciar sesión. Inténtalo de nuevo.` |

## Data / API Contract

No worker API change is required for this story.

Frontend auth contract:

```ts
await supabase.auth.signInWithPassword({
  email: string,
  password: string,
});
```

The important output is:

- `data.session` → indicates successful login and provides `access_token`
- `error` → mapped to user-friendly Spanish copy

## Testing Plan

### Manual / UI verification

- `/auth/login` shows email and password fields
- Password input obscures typed characters
- Invalid credentials keep the user on the page and show a Spanish error
- Successful login redirects to `returnTo` when present
- Successful login falls back to `/` when `returnTo` is absent
- Reloading the page still shows the user as authenticated through the persisted Supabase session

### Follow-up integration verification

Once US-05 is implemented:

- Start from a guest CTA on `/{slug}`
- Log in successfully
- Confirm the user returns to the same business page and can submit a review

## Risks / Open Questions

| Risk                                                   | Mitigation                                                               |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| `returnTo` could be abused as an external redirect     | Only allow values beginning with `/`                                     |
| Raw Supabase errors may be too technical or in English | Map common auth failures to short Spanish messages                       |
| Supabase env vars may be missing locally               | Keep the existing `supabase.ts` guard and document setup in `.env.local` |
